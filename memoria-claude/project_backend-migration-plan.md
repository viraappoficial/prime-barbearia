**UPDATE (2026-07-20): This migration is DONE, not planned.** Gabriel confirmed Prime is already running on Supabase (verified: `supabase` references present in [index.html](../../../../Downloads/prime/index.html), [ROADMAP.md](../../../../Downloads/prime/ROADMAP.md), [PLANO-RESPOSTA-INCIDENTE.md](../../../../Downloads/prime/PLANO-RESPOSTA-INCIDENTE.md), and [sw.js](../../../../Downloads/prime/sw.js)). Gabriel now runs one Claude Code session per project — a separate SEHORBAS union-site project is being built in a sibling directory and will get its own separate Supabase project under the same account (not a new account). The history below (why the migration happened, hosting decisions, security concerns) is kept for context but the "don't start without asking" framing is stale — verify current state in the actual code/ROADMAP before assuming anything below still applies.

Gabriel wanted to move away from the original `localStorage`-only architecture toward a real backend/database, so client data persists centrally, syncs across devices, and clients can be filtered by date range (e.g. "clientes da semana"). He also wanted LGPD compliance planned in.

**Why:** Right now every barber's client list, sales, appointments, etc. live only in that barber's own browser `localStorage` — two barbers logging in on two different phones do not see the same data. This isn't just a future scaling concern, it's a real limitation of the app today. Filtering clients by week/period is also hard to do well client-side without a real query layer.

**How to apply:** When this work starts, recommend Supabase (Postgres-managed, generous free tier, plugs into vanilla JS incrementally without a full rewrite, row-level security fits the "barber only sees own clients" access rule) over Firebase/Firestore, since the data model (barbers, clients, sales, appointments) is naturally relational. This is flagged as the single largest architectural change the project could undergo — it touches nearly every `localStorage.getItem/setItem` call across [index_9.html](../../../../Downloads/prime/index_9.html). Full plan and LGPD checklist are written out in [ROADMAP.md](../../../../Downloads/prime/ROADMAP.md) under "Fase 6 — Backend Real & Conformidade LGPD" (added 2026-07-08). Don't start this migration without Gabriel explicitly asking — he deferred it intentionally, this memory + the roadmap section are just so the plan survives across sessions.

**Hosting/cost plan** (discussed 2026-07-08, nothing purchased yet): explicitly decided AGAINST buying a VPS/dedicated server — Gabriel is not a developer and self-managing a server (OS patching, DB admin, backups, security) is real sysadmin overhead disproportionate to a single barbershop's scale. Recommended stack: Supabase for the database (free tier to start, ~US$25/mo Pro only if the business genuinely outgrows it — no server administration needed either way), and either keep GitHub Pages or move to Vercel/Netlify for the static site (all free, Vercel/Netlify auto-deploy on `git push` which fits the existing workflow). Only realistic recurring cost is an optional custom domain (~R$40-60/year via registro.br) — cosmetic/professionalism, not required for the system to work. If Gabriel asks about hosting again, this is the answer — don't suggest a dedicated/self-managed server.

**Security urgency raised** (2026-07-10): the site isn't in real use yet (no real client/barber accounts using it live), but Gabriel confirmed this is heading toward a serious product with real accounts for both clients and barbers. Flagged that today barber passwords are stored and compared in **plain text** in the client-side JS (`b.pass===p.value` in `baLogin()`, [index_9.html](../../../../Downloads/prime/index_9.html)) — anyone with browser devtools access on a barber's device can read every barber's password. This is unrelated to hosting choice (Vercel vs paid makes zero difference here) — it's a data-architecture problem that only the Supabase/backend migration actually fixes (real hashed auth, server-side validation, RLS instead of client-side-only filtering). Agreed plan: since the site isn't live yet, finish the current feature roadmap first, then migrate to Supabase **before** onboarding real accounts with real passwords — don't launch real multi-user accounts on the current localStorage architecture.

**Storage sizing discussion** (2026-07-10): Gabriel worried the ~500MB free-tier Postgres database would fill up fast, especially with client photos. Clarified: structured data (clients, sales, appointments) is tiny (~0.5-1KB/row) — even thousands of records over years stays well under 500MB. Photos are the real concern and live in a **separate** Supabase Storage quota (not the DB's 500MB) — but even that fills fast with unoptimized phone photos (2-8MB each) vs compressed ones (100-300KB each, ~10-20x more headroom). Resulting hard rule for any future photo feature (e.g. "Meu estilo", paused) — noted directly under that item in ROADMAP.md Fase 3: always client-side compress/resize images before upload (e.g. max 800px width, ~80% JPEG quality) and lazy-load galleries (only fetch visible images). This must ship with the first version of any photo feature, not bolted on later.
